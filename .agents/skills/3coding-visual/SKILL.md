# 编程实现与数据图表生成

本 skill 承接 `2analysis-modeling`。目标是把 `reports/ANALYSIS_MODELING_REPORT.md` 里的模型和算法落实为可复现程序，跑出可信结果，并生成论文中需要的数据型图表。

代码事实验证由 `verify-generated-code` 提供。开始本阶段时必须读取该 skill；不得只靠文字说明声称环境、API、依赖或结果已经验证。

开始时同时读取 `../_references/learning_project_contract.md` 和 `../_references/python_engineering_standard.md`。代码风格按有丰富数值计算和算法开发经验的工程师标准执行。

## 人工审批边界

开始时读取 `../_references/approval_gates.md`，并确认 `plan.md` 中 G1 为 `APPROVED`。否则停止并请求先批准建模方案。

本 Skill 分两轮执行：

- G2 最小代码验证：只实现足以验证数据管道、模型可行性和关键约束的最小版本，提供基线或小规模结果、异常记录和少量诊断图。
- G3 完整实验：仅在 G2 批准后运行完整数据、正式调参、对比实验、灵敏度/稳健性分析并生成论文用数据图表。

G2 提交后必须停止，不得在同一轮自动进入完整实验。G2、G3 提交前分别更新 `reports/QUALITY_SCORECARD.md` 的代码与实验、模型与数学、图表证据和未关闭缺陷。

## 数学建模规范参考

如需领域判断，读取 `../_references/math_modeling_norms.md` 中的“题型防错速查”“代码实现与结果”“编码阶段常见错误”和“图表与可视化”小节。该文件只作为规范知识库，不新增本阶段的固定产物。

## 阶段边界

- 本阶段负责：代码、实验运行、结果、结果表、数据驱动图表。
- 本阶段不负责：技术路线图、算法流程图、系统架构图、概念示意图。这些交给 `4drawio`。
- 本阶段不写论文正文，只为 `5writing` 提供可信数值和图表资产。

## 强制环境契约

写代码前按以下优先级确定 Python：用户明确指定、`MATHMODEL_PYTHON`、`.codex/runtime.local.json`、项目 `.venv`、PATH 候选。始终记录并调用解释器绝对路径，不直接假定 `python` 或 `python3` 指向 VS Code 选择的环境。

使用 `verify-generated-code` 运行 `preflight`。至少记录 `sys.executable`、Python 版本、平台、实际 imports 和包版本。解释器不存在或探测失败时停止；不得静默换用另一个 Python。


### Step 1: 代码结构

按 `plan.md` 中“项目目录结构”创建 `code/`、`tests/`、`results/`、`figures/` 和 `logs/` 骨架，再开始写代码。默认使用 `code/main.py` 单文件主实现，在文件内清晰划分配置、异常、数据层、模型层、验证层、可视化层和 CLI。子问题数按赛题实际数量调整，不按问题数机械拆文件。

同时创建 `code/audit_manifest.json`，列出 G2、G3 和 final 阶段可直接执行的入口、参数、超时和预期产物。不得把多个命令拼成 shell 字符串；外部 API、求解器和 CLI 必须记录证据状态。

在项目根创建 `tests/`，测试文件使用 `test_*.py`。`main.py` 内的数据读取与校验、特征构造、模型求解、评价指标和绘图必须是可独立调用的逻辑单元；入口函数只负责解析参数和编排流程。若单文件明显损害可维护性，可在报告中说明后拆成少量模块。

### Step 1.5: 代码质量契约

正式代码必须完整执行 `python_engineering_standard.md`。特别强调：

- 用 `dataclass` 或集中字典管理配置，用 `logging` 取代 `print`，区分数据、数值和配置异常。
- 核心函数使用适量类型注解与 Google/NumPy 风格 docstring；辅助函数不过度注解。
- 函数单一职责且原则上不超过 50 行；超长算法内核要说明理由并增加测试。
- 按需使用 log-sum-exp、`np.clip`、`np.linalg.solve`、`scipy.special`、稀疏矩阵、Numba 或内存映射，不为展示技术栈强行使用。
- 只有真实完成旧实现比较和计时后，才能保留“旧实现慢 N 倍”等 1–2 处版本演进注释；不得伪造人工痕迹。
- 测试导入 `code/main.py` 时避免把 `code` 当作包名遮蔽 Python 标准库。
- 绘图函数接收已保存的结果数据，不重新计算或改写核心指标。
- 记录 Python 和依赖版本、随机种子、运行参数、开始/结束时间、耗时和产物哈希。

使用项目确认的解释器执行静态检查和测试：

```powershell
& "<python.exe>" -m ruff check code tests
& "<python.exe>" -m pytest -q tests
```

不得裸调用 `ruff` 或 `pytest`。工具未安装时标记为 `UNVERIFIED`，列出缺失依赖并等待安装批准；不得把“未执行”写成通过。


### Step 2: 逐子问题实现

按子问题顺序实现，不要一次性写完不跑。

每个子问题必须完成：

1. 读取所需数据。
2. 实现模型或算法。
3. 验证约束。
4. 输出核心结果。
5. 绘制丰富的图表。
6. 在 `reports/RESULTS_REPORT.md` 中写清楚方法、关键数值和校验结果。
7. 对概率、权重、梯度、约束、矩阵条件数或物理范围执行与题型相符的数值验证。

优化类问题必须先保证可行解，再优化目标值。预测类问题必须做训练/验证划分或合理误差评估。评价类问题必须说明指标方向、归一化方法和权重来源。

### Step 2A: G2 最小代码验证

先为每个关键模型建立最小可行实现，至少报告：

- 数据能否成功读取和完成最小预处理。
- 基线方法或可行解。
- 关键约束是否满足。
- 一个能揭示模型是否异常的诊断结果。
- 当前运行时间、失败点、风险和完整实验预计成本。

G2 测试至少覆盖一个正常小样本、一个边界输入和一个失败输入。根据题型选择空数据、缺失值、重复记录、零值或负值、极端参数、不可行约束、错误形状、未知类别、单类别、时间边界等案例；测试应验证明确的数值、异常类型或约束状态，不能只断言“程序没有报错”。测试期望值不得完全复用被测实现中的同一公式。

若使用数值优化并提供解析梯度，在 G2 执行有限差分梯度检查；不适用时在结果报告中说明。关键权重归一化等内部不变量使用容差断言，例如 `assert np.allclose(weights.sum(), 1.0)`。

将结果写入 `reports/RESULTS_REPORT.md` 的“最小代码验证”部分，按审批协议提交 G2 并停止。不要把试运行结果冒充正式论文结论。

提交 G2 前，使用选定解释器运行 `verify-generated-code` 的 `g2` 审计。只有审计状态为 `VERIFIED` 才能把代码称为“已验证”；`FAILED` 必须修复，`UNVERIFIED` 必须在审批材料中明确列出且不得声称可运行。

### Step 2B: G3 完整实验

只有 G2 获批后才执行原 Step 2 的完整计算和后续步骤。增加必要的基线比较、消融或替代模型、灵敏度/稳健性检查；不适用时说明理由。

G3 前补齐所有公开计算接口的单元测试，并为每个子问题保留至少一个确定性端到端小样本测试。修复 `ruff` 错误和 `pytest` 失败后再运行正式实验；确需忽略的静态规则必须在代码附近用中文说明原因并在结果报告中登记。

提交 G3 前运行 `g3` 审计。正式实验过慢时可以保留已有正式运行日志和产物哈希，但必须另外成功执行清单中的确定性小样本重放；不得只做源码扫描。

### Step 3: 结果文件格式


AI 在实现、求解和作图过程中，必须把关键中间过程保存成数据并做好记录，例如清洗后的数据摘要、模型参数、迭代历史、约束检查、灵敏度分析过程、图表所用数据和运行日志。中间数据优先保存到 `figures/` 或 `code/outputs/`，并在 `reports/RESULTS_REPORT.md` 中说明文件用途。

`reports/RESULTS_REPORT.md` 推荐结构：

```markdown
# 计算结果

## 运行环境
## 数据读取与预处理
## 问题一结果
## 问题二结果
## 问题三结果
## 灵敏度分析
## 约束与一致性校验
## 与建模报告的一致性说明
## 可复现运行方式
## 代码证据审计
```

所有数据和图表结果都必须出现在 `reports/RESULTS_REPORT.md` 中引用

### Step 4: 生成数据驱动图表

根据 `reports/ANALYSIS_MODELING_REPORT.md` 和 `reports/RESULTS_REPORT.md` 规划图表，生成 PDF 到 `figures/`。

典型图表：

- 预测类：真实值-预测值对比、误差分布、指标对比。
- 优化类：收敛曲线、成本对比、资源利用率、方案前后对比。
- 评价类：综合得分排序、雷达图、热力图、敏感性曲线。
- 数据理解：分布图、趋势图、相关性图、箱线图。

图表要求：

- PDF 矢量输出，适合论文。
- 同时支持 SVG；需要快速预览或存在栅格元素时再输出高分辨率 PNG。
- 不在图内写大标题，标题交给论文 caption（Typst 的 `caption:` 或 LaTeX 的 `\caption{}`）。
- 中文论文图表使用中文坐标轴和图例；英文论文使用英文。
- 不生成流程图/架构图/路线图。
- 同一论文使用统一字体、字号层级、线宽、标记和色板；颜色在灰度打印和常见色觉缺陷下仍可区分。
- 位图照片或无法矢量化的栅格图按最终排版尺寸至少 300 DPI，纯线稿建议 600 DPI；统计图优先保留矢量文字和路径。
- 导出后逐图检查字体嵌入、中文缺字、图例遮挡、坐标裁切、标签重叠、异常留白和数据点遗漏。

图表可以由主程序或独立脚本生成，不强制固定脚本名。无论采用哪种方式，都必须保存图表对应的数据来源和生成记录。

完整结果和正式数据图完成后，生成“关键数值核对表”和“一键复现方式”，按审批协议提交 G3 并停止。G3 批准前不得进入论文写作。

G3 交付必须是一整套：`code/main.py`、测试、依赖记录、运行日志、结果数据、图表及其源数据、审计证据和复现命令，不得只交代码片段或截图。

“代码证据审计”必须引用 `reports/code-audit/g2/audit.json` 或 `reports/code-audit/g3/audit.json`，列出解释器绝对路径、审计状态、成功入口、外部接口状态和正式产物哈希。不得在报告中记录密钥值。
