# 生成代码证据审计

把“代码看起来合理”与“代码已在指定环境中得到验证”严格分开。使用确定性脚本收集证据；不要凭记忆声明工具、包、API 或运行结果可用。

用于数学建模项目时，先读取 `../_references/python_engineering_standard.md`。审计应验证用户要求的单文件主实现、数值稳定性、错误处理、测试、日志和复现证据，而不是强制把代码拆成多个模块。

## 状态语义

- `VERIFIED`：存在可复查的本机探测、成功运行或产物证据。
- `UNVERIFIED`：尚未运行、外部接口不可访问、证据不足或只验证了部分路径。
- `FAILED`：语法、依赖、运行、产物或声明与证据冲突。

不得把 `UNVERIFIED` 改写为“应该可用”。Mock、模拟数据和 fallback 必须明确标注，不能作为正式结果证据。

## 解释器解析

按以下顺序选择 Python，并记录绝对路径：

1. 用户明确指定的解释器。
2. `MATHMODEL_PYTHON` 环境变量。
3. 项目 `.codex/runtime.local.json` 的 `python` 字段。
4. 项目 `.venv/Scripts/python.exe` 或 `.venv/bin/python`。
5. PATH 中的 `python`；此项只能作为待确认候选，先输出 `sys.executable` 再使用。

禁止因为 VS Code 能运行代码，就推断当前终端使用同一解释器。禁止静默切换到另一个“碰巧可用”的 Python。

## 审计工作流

### 1. 建立运行清单

在项目中创建 `code/audit_manifest.json`。格式和接口证据要求见 [evidence-policy.md](references/evidence-policy.md)。每个需要声称已运行的入口都必须列入清单，不使用 shell 拼接命令。

### 2. 运行确定性审计

使用选定解释器运行：

```powershell
& "<python.exe>" "<skill-dir>/scripts/audit_code.py" --root . --stage g2
```

阶段可为 `preflight`、`g2`、`g3` 或 `final`。脚本检查实际解释器、版本、平台、包、Python 语法、顶层 imports、静态风险、入口退出码、日志、预期产物和 SHA-256 哈希。

输出写入 `reports/code-audit/<stage>/audit.json` 和对应运行日志。

审计同时执行代码质量门禁：

- 使用当前解释器运行 `python -m ruff check code tests`；记录 Ruff 版本、退出码和完整日志。
- 使用当前解释器运行 `python -m pytest -q tests`；记录 Pytest 版本、收集数量、通过/失败/跳过数量和日志。
- 扫描核心公开 API 的类型标注与规范 docstring、关键设计注释、函数长度、分支复杂度、过多参数、重复职责和宽泛异常。
- 检查 `tests/` 是否包含真实边界/异常测试，且测试期望没有直接调用被测实现重新计算自身答案。
- 工具不存在、没有测试或未发现边界测试时标记为 `UNVERIFIED` 或 `FAILED`，不得只凭入口成功运行判定代码质量通过。

### 3. 执行阶段门禁

- `preflight`：解释器必须真实存在并可运行；代码可以尚未创建。
- `g2`：至少一个最小入口成功运行，关键 imports 可解析，预期基线产物存在。
- `g2`：同时要求 Ruff 无未批准错误、Pytest 成功，并至少存在正常、边界和失败输入测试证据。
- `g3`：正式入口和论文将引用的结果产物必须成功生成；Ruff 与完整测试必须通过。完整实验过慢时可复用已有正式运行记录，但必须另外成功运行确定性小样本重放。
- `final`：至少重跑所有轻量入口、Ruff 和测试并核对正式产物哈希；不得仅扫描源码后判定通过。

`FAILED` 时停止当前阶段并修复。`UNVERIFIED` 时不得提交“已验证”结论；列出需要用户提供的文档、凭据或运行条件。

## API、工具与环境事实

- 第三方 Python API：优先使用安装包反射、包版本和最小调用验证；需要文档时只使用官方文档或用户提供的版本化文档。
- 外部 CLI：记录解析后的绝对路径、`--version` 输出和实际最小命令。命令不存在时不得编造替代工具。
- 网络 API：不得虚构端点、参数、响应字段或凭据。无法访问时把接口标为 `UNVERIFIED`，使用 Mock 只能验证调用结构。
- 环境变量和密钥：只记录变量名和是否存在，绝不把值写入报告或日志。
- 自动 fallback：只有在报告中记录触发原因、替代路径和结果影响时才允许；不得吞异常后伪装成功。

## 可维护性判定

- 核心公开 API 缺少必要类型标注或 Google/NumPy 风格 docstring 时标记 `UNVERIFIED`；辅助函数不要求过度标注。
- 单函数超过 50 行时要求拆分或记录算法连续性理由；超过 80 行且没有合理说明时标记 `FAILED`。
- 若代码声称使用 log-sum-exp、梯度检查、Numba、稀疏矩阵、内存映射或“快 N 倍”，必须找到实际调用、测试、基准或日志证据；只写注释或导入包不能视为实现。
- 检查项目是否记录依赖版本、随机种子、运行时间和产物哈希，并确认 `logging` 用于运行日志。
- 代码文件超过 40 个有效行却没有任何解释公式、约束、单位或设计理由的中文注释时标记 `UNVERIFIED`。
- 测试只覆盖顺利路径、只断言非空、或测试与实现复制同一错误公式时，不能作为边界与正确性证据。

## 与数学建模工作流的连接

- G2 前先运行 `preflight`，G2 提交前运行 `g2`。
- G3 提交前运行 `g3`，把审计结论和产物哈希写入 `RESULTS_REPORT.md`。
- `6verity` 运行 `final`，把结果写入 `VERIFY_REPORT.md`。
- 本 skill 不新增人工审批点；它是 G2、G3 和最终验收内部的强制证据门禁。
